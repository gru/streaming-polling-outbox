# AGENTS.md

Исследовательский стенд: сравнение двух способов доставки outbox-сообщений из PostgreSQL 17 в Kafka — **SQL Polling** (`pg_logical_slot_peek_binary_changes()` + advance) vs **Npgsql Streaming Replication** (`PgOutput`). Доставка — logical replication через слот; SELECT-polling таблицы запрещён. Git-репозиторий, ветка `main`.

## Документы (читать перед работой)

- `requirements.md` — **единый авторитетный spec** (объединяет `prd.md` и `prd-2.md`; правила prd-2 по WAL retention имеют приоритет). Все детали: роли, HA-тесты TEST-HA-001…008, метрики, план этапов 1–10, критерии готовности, риски RISK-001…010.

- `README.md` — быстрый старт и полезные команды.

Размеры пачек настраиваются env (см. таблицу в README). Проверено сквозным прогоном: 500/500 уникальных id в Kafka, 0 потерь, 0 дублей, confirmed_flush == gauge после delivery.

## Критические жёсткие ограничения (requirements.md, раздел 2)

Нарушение любого из них ломает цель исследования:

- Механика CDC — **outbox-таблица + pgoutput** (финальное решение владельца; история и причины — docs/deviations.md раздел 1: pgoutput не передаёт logical messages ни в одной версии PostgreSQL — связка из ТЗ доказанно неработоспособна; test_decoding отклонён как не-production). Запрет ТЗ на outbox-таблицу снят решением владельца, но SELECT-polling таблицы по-прежнему запрещён: чтение только через logical slot (peek/advance и стриминг).
- Никакой outbox-таблицы и никакого polling таблицы вместо logical replication.
- KafkaFlow — основной API публикации (Confluent.Kafka допустим только как внутренняя зависимость).
- .NET 8 строго (`net8.0`), PostgreSQL строго 17, всё в Docker Compose.
- Никакого SUPERUSER для прикладных ролей; LSN подтверждается только после Kafka delivery (at-least-once, дубликаты допустимы, потери нет).
- Не использовать Patroni permanent replication slots для logical slots — failover slots синхронизирует сам PostgreSQL 17.
- Не скрывать потери WAL / ошибки; не подменять реальные результаты тестов предполагаемыми цифрами.

## Ключевые технические грабли

- **Остатки от предыдущих прогонов/раскладок НЕ чистятся кодом инициализации.** Init-скрипты только создают объекты идемпотентно (CREATE IF NOT EXISTS). Если есть подозрение, что в стенде что-то осталось от прошлого прогона (чужая БД, слот с другим плагином, лишние роли) — не дописывать миграции в init, а полностью очистить стенд: `./scripts/reset/wipe.sh` (docker compose down -v) и поднять заново.
- `max_slot_wal_keep_size` считается от **фактически измеренного объёма WAL** (разница LSN), НЕ от размера payload; в нормальных тестах `-1`, лимит только в отдельном WAL Pressure Test.
- **pgoutput не эмитит logical messages** (ни в одной версии PG, проверено на 17.2/18.4) — поэтому доставка идёт через INSERT в `public.outbox_messages` (publication `outbox_publication` содержит эту таблицу: pgoutput эмитит только опубликованные таблицы). Слот `outbox_slot`: плагин `pgoutput`.
- Одна вставленная строка в pgoutput = несколько протокольных записей (Relation + Insert, плюс B/C-обрамление транзакции): не считать каждую бинарную запись отдельным событием (requirements.md 7.1 — теперь это буквально применимо).
- Жизненный цикл строк outbox решён архитектурно: Writer делает INSERT+DELETE в одной транзакции, таблица всегда пустая, сообщение живёт в WAL. CDC будет получать Delete-записи pgoutput — их надо игнорировать (не считать ошибкой/событием).
- **DELETE с WHERE в PostgreSQL требует SELECT на колонки условия** (docs: «the SELECT privilege on any column whose values are read in the condition») — поэтому у sys_writer колоночный `GRANT SELECT (id)`, а не табличный SELECT; полный SELECT (body) запрещён.
- **Никогда не запускать `docker compose up`/`run` без `--no-deps` на живом стенде** (и не указывать сервисы, от которых зависит pg): compose реконсилят весь граф зависимостей и могут пересоздать pg-контейнеры — одновременный рестарт всех нод Patroni = флап промоушенов и рассинхрон failover-слотов (наблюдалось: 6 промоушенов за 15 минут, wal_status=lost у копии слота). Пересборка/перезапуск одного сервиса: `docker compose build writer && docker compose up -d --no-deps writer`; полный рестарт — только через `./scripts/reset/wipe.sh`.
- **HAProxy резолвит имена pg1-3 один раз при старте**: после пересоздания pg-контейнеров (новые IP) haproxy продолжает стучать в старые → все backends down («server closed the connection unexpectedly»). Лечение: `docker compose restart haproxy`.
- Прикладная БД — **`outbox`**, не `postgres` (решение владельца; все psql прикладных запросов — `-d outbox`): PG17 slotsync worker синхронизирует слоты только БД из `dbname` в `primary_conninfo`. Реализовано БЕЗ патчей Patroni (запрещены владельцем): официальная опция `postgresql.database: outbox` + официальный кастомный bootstrap-метод `bootstrap-with-appdb` (создаёт БД в PGDATA до первого SQL Patroni — без него bootstrap тупик: management-подключения Patroni идут в ту же БД, которой после initdb нет). Проверено: `SHOW primary_conninfo` на стендбаях содержит `dbname=outbox`.
- **Непотребляемый слот со временем перестаёт синхронизироваться** (воркер: `could not synchronize ... remote slot precedes local slot` — catalog_xmin стендбая обогнал слот): при promotion такой слот НЕ сохраняется («to avoid data loss»). Это документированное поведение PG17, не баг — полная механика с цитатами из документации: `docs/deviations.md` раздел 3 и [PG17 §47.2.3](https://www.postgresql.org/docs/17/logicaldecoding-explanation.html#LOGICALDECODING-REPLICATION-SLOTS-SYNCHRONIZATION). До появления CDC перед failover-экспериментами продвигать слот вручную на primary (`pg_logical_slot_get_binary_changes` в БД `outbox`; peek НЕ продвигает); реальный CDC делает это сам после Kafka delivery. После demotion у старого leader остаётся несинхронизированный остаток слота — лечит `./scripts/init/apply-bootstrap.sh` (03-slot-reconcile.sql). `synced=true` у слота на новом leader после promotion — норма (промоушен синхронизированной копии).
- **Патчи Patroni запрещены владельцем.** Нестандартные потребности — только официальными механизмами (кастомные bootstrap-методы, `postgresql.database`, pg_hba/parameters в patroni.yml).
- Кластерные параметры (`wal_level` и др. из `CMDLINE_OPTIONS` Patroni) применяются только через `bootstrap.dcs.postgresql.parameters` (DCS); member-local `postgresql.parameters` для них игнорируются — иначе standby падает с FATAL slotsync worker'а.
- Publication не фильтрует logical messages — не считать её границей доступа.
- Polling читает через `peek` (не `get_changes` — тот потребляет до подтверждения Kafka); advance — только через SECURITY DEFINER-функции с зафиксированным слотом.
- Streaming подключается к PostgreSQL напрямую, минуя PgBouncer; Writer — по умолчанию через PgBouncer (`pool_mode = transaction`).
- Разделять понятия: внутренний batching Kafka producer ≠ прикладной batch ≠ подтверждение LSN.
- Инвалидированный слот ≠ пересоздать молча: явная ошибка с диагностикой.
- Несинхронизированный остаток слота на реплике возникает, когда старый primary возвращается в кластер как standby со своим оригинальным слотом (synced=false): при failover-слоте с тем же именем на новом primary slotsync worker завершается с "same name slot ... already exists on the standby" (полный рестарт стенда провоцировал гонки промоушенов — тот же случай). Synced-копии рестарты переживают штатно: synced — поле on-disk состояния слота, воркер обновляет копии на месте (проверено рестартом pg2 на 17.2). Остаток роняет 03-slot-reconcile.sql; случай "remote slot precedes local slot" (WAL/каталоги) им не лечится — там продвижение слота на primary (deviations.md раздел 3).
- `synchronized_standby_slots` принимает только ФИЗИЧЕСКИЕ слоты; пишется через ALTER SYSTEM локально — после смены primary перезапустить apply-bootstrap.sh.
- PgBouncer: userlist с plaintext-паролями генерируется init-db из .env (SCRAM pass-through с верификаторами из pg_authid на этой сборке не работает); хост-порт HAProxy 5432 (занявший его раньше airo-postgres остановлен вручную, policy unless-stopped).
- **Writer (этап 3)**: UUID (v7, свой `MessageFactory.CreateUuidV7` — `Guid.CreateVersion7` только в .NET 9; поля Guid-span little-endian, version-нибл в байте 7) и `created_at` задаёт клиент — у `sys_writer` только INSERT+DELETE и колоночный SELECT(id), `RETURNING` требует SELECT на возвращаемые колонки. Один батч = multi-row INSERT + DELETE тех же id в одной транзакции; ретрай тех же UUID после сбоя: `unique_violation` по PK на повторе = «прошлый commit прошёл» (так разрешается неоднозначный commit 6.3, дублей в outbox нет). У источника PgBouncer `No Reset On Close=true`. Мягкий stop прерывает только ожидание между ретраями — начавшийся commit доигрывается; жёсткая отмена (shutdown хоста) оставляет батч «неоднозначным». Сборка/тесты .NET — в контейнере `mcr.microsoft.com/dotnet/sdk:8.0` (локальный dotnet — 10-й); хост-порт Writer 18080 (8080 занят контейнером airo-host другого проекта).
- **CDC Polling (этап 4)**: SECURITY DEFINER-функции `cdc.peek_outbox_changes(limit)` / `cdc.advance_outbox_slot(target)` / `cdc.outbox_slot_status()` в БД `outbox` — слот/publication/proto_version жёстко зашиты, лимит зажат 1..10000, advance дальше watermark `cdc.peek_state` отклоняется («не подтверждай то, что не читал»; watermark и строки peek — одна транзакция). Прямой peek от sys_app падает `permission denied to use replication slots` (привилегия REPLICATION; см. deviations.md) — поэтому wrapper без повышения роли.
- **.NET env-префикс CDC — `CDCPOLLING__`, НЕ `CDC_POLLING__`**: провайдер EnvironmentVariables заменяет на `:` только двойные подчёркивания, одинарные остаются в имени ключа (`CDC_POLLING__X` → секция `CDC_POLLING`, а биндится `CdcPolling` — значения молча теряются; ловили на пароле). У Writer (`WRITER__`) проблемы нет — имя без подчёркиваний.
- **Профили compose**: cdc-polling живёт в profile `polling` — `docker compose up -d` его НЕ поднимает; запуск/пересоздание всегда с `--profile polling` и `--no-deps`. Два CDC одновременно на одном слоте запрещены (requirements.md 11); конкурентный peek/advance на занятом слоте даёт SQLSTATE 55006 (движок классифицирует как транзиентный).
- **Relation-запись pgoutput содержит байт replica identity** между именем таблицы и числом колонок (`'d'` = default) — без него ncols читается мусором (25600) и батч падает в парсере; байт есть в proto v1, но часто забывается. Ещё: флаг колонки PK = 1.
- **LSN для advance — строчный LSN Commit-записи peek** (внутри сообщения это `end_lsn`, позиция сразу после commit-записи; `pg_replication_slot_advance` ставит confirmed_flush ровно на него — сверено на стенде). Advance возвращает `(slot_name, end_lsn)` во ВСЕХ версиях — колонки `end_xid` не существует ни в одной официальной (проверено 17/18/19/devel; ранее ошибочно приписывал PG18). Колонки `persisted` в `pg_replication_slots` тоже нет нигде: «persistent slot» в доках §47.2.3 — это «не temporary», а не колонка; в PG17 представление пополнилось `failover` и `synced`.
- **KafkaFlow 4.2.0** (единая для всех CDC-сервисов): `WithAcks(KafkaFlow.Acks.All)` (у KafkaFlow свой enum `Acks` — конфликтует с Confluent.Kafka.Acks, квалифицировать!), `WithProducerConfig(new ProducerConfig { EnableIdempotence = true, ... })` — extension-метод `KafkaFlow.ConfigurationBuilderExtensions`; value идёт через ISerializer (пасsthrough для byte[]), string-key конвертируется сам (UTF8). `ProduceAsync` ждёт delivery-репорт.
- **Метрики OTel Prometheus**: порядок label'ов не фиксирован (`otel_scope_name` может быть первым) — grep'ы проверок писать по строке метрики + label, а не по «имя{kind=…}». Счётчик без единой записи не экспортируется вовсе.
- check-infra.sh и smoke-writer.sh знают о живом CDC: при запущенном cdc-polling их live-peek проверки пропускаются (слот потребляется CDC, конкурентный peek = 55006); smoke-cdc-polling.sh проверяет доставку полным циклом.

## Роли PostgreSQL

`sys_writer` (запись, NOREPLICATION), `sys_app` (polling через SECURITY DEFINER-функции), `sys_replication` (REPLICATION, streaming), `postgres` (админ). Пароли через env, не в коде.
